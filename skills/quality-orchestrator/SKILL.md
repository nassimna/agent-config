# Quality Orchestrator

Keep the human's attention on decisions while agents discover, reproduce, fix and
verify real application problems. One coordinator owns canonical state, queue,
PR watches and reporting; bounded children implement and verify. Reuse existing
project tooling and records rather than adding an orchestration framework.

## Establish the project contract

Read existing instructions, maps, source patterns and current work first. Use
[the project contract](references/project-contract.md) to record the target/base,
environments, data freshness, permissions, resources, proof and delivery mode in
the existing private state directory. Reuse observable settings; ask only for
missing authorization or a genuinely consequential decision. Never carry branch
names, credentials, fixture or merge permissions over from another project.
Preparation is not activation. Start only when explicitly authorized.

Honor a named base for EVERY implementation/review/integration worktree and PR.
Refresh the clean owned coordinator's committed base before isolated delegation,
since T3 worktree children start from the parent commit. Preserve required task
commits and pin the reviewed candidate; never reset dirty/shared work or fabricate
child worktrees in shell. Transfer existing ownership safely before migration.

## Discover and confirm

Maintain coverage and root-cause fingerprints, prioritizing changed code and
least-covered flows. Run bounded source review alongside a user-journey job when
capacity permits. Source candidates remain hypotheses until reproduced through
the actual affected application path. User scouts enter through login/navigation
and finish intended tasks, including meaningful failure/recovery and role/language
states. Opening a page is not a passed journey.

Capture loading/interaction/request evidence during user journeys. Confirm
worthwhile performance candidates with comparable staging measurements and
attribution; local development timing is only a lead. Serialize heavy builds,
browser ownership, deployments and timing. Default cap: two children, one heavy
owner and one active implementation, unless the project explicitly sets another.

When current staging data copying is authorized, refresh through existing tools
before a meaningful local validation batch and clone it into disposable local
state. Include referenced objects, schema/revision, export time, source role/data
scope and manifest. Preserve business records while replacing copied credentials
and disabling jobs/providers. Keep raw snapshots private. Reuse the batch baseline
while unchanged; refresh after relevant staging deployment/data changes. Record
non-atomic export or mid-copy drift rather than claiming exact live equivalence.
If capture brackets show relevant serving/schema/data drift, retry the refresh
once after the source stabilizes before parity-dependent local validation. If it
still drifts, hold that acceptance and report the actual mismatch; do not keep
exporting or label the copy current. No authorization to refresh means use the
permitted source and disclose limits.

## Deliver one finding

One confirmed root cause gets one focused branch/PR, not a new top-level chat.
Before implementation identify the actual contract, nearest working pattern,
minimal delta and required proof. Use developer-workflow and ai-slop-cleanup;
reject speculative abstractions, cosmetic PR quotas and scope growth. Cleanup-only
work needs demonstrated maintenance cost and preservation evidence.

The coordinator invokes council for independent Claude/GPT source review and
assigns separately required independent runtime/staging verification. Children
never recruit reviewers or watch/merge PRs. Use file-pr for concise problem/result,
review outcomes and decisive sanitized evidence. Keep bug/performance PRs draft
until all project source, tests/CI, exact-candidate staging and cleanup gates pass.
Scores, green CI and empty hosted pages do not replace actual acceptance.

Classify the complete candidate. If explicitly authorized by this project's
contract, automatically merge noncritical fixes preserving intended UI/UX only
after fresh head/base/check/review/mergeability and all proof gates pass. Critical,
intentional UI/UX or uncertain changes use full-stop for human review; an explicit
full-stop request always remains unmerged. Without automatic-merge permission,
use full-stop for every PR. Preserve protection and publication boundaries; verify
post-delivery behavior before resolved. Never infer production permission.

## Continue and report

Use current native/T3 routing and fresh self-contained briefs for new/recheck
jobs. Record task/head/base/results and explicit resource release. Drain supported
completion/PR events, deduplicate and dispatch the next useful job without routine
human prompts. A finished discovery pass selects the next due/uncovered goal;
stop quietly when no useful work is due or authorization truly blocks it.
Never poll running delegates, create per-finding top-level threads or retry an
unchanged failure in a loop. Parent alone owns the event-driven PR watch.

Use one daily human digest in the coordinator at the agreed local time; routine
progress and unchanged blockers stay internal. Deduplicate urgent risks and
required user-only decisions. Maintain date/completion/report provenance.

A recovery watchdog must be a supported lightweight host gate that wakes only for
missed completion/due work or a confirmed long stall, accounting for active
children, deadlines and healthy CI waits. Native unconditional LLM timers are not
conditional watchdogs. Use idempotent recovery claims; never stop a healthy owner.
If no supported gate exists, record the gap without pretending recovery works.
Validate scoped success/failure/permission cases with evaluate-agent-skills before
broad reliance. On authorized activation, establish ownership and schedule binding,
then run one bounded real discovery or accepted-finding pilot; inspect its actual
receipts before refilling the worker pool. A discovery-only pilot does not prove
the full fix/PR/delivery pipeline, and no finding is invented to complete a pilot. Separate simulation, live operation
and app-level child visibility/notification claims.
